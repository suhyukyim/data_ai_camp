# 객체 탐지 모델 조사 (섹션 0 과제)

## 학습 내용

과제 기본 지정 모델인 YOLO 외에 다른 객체 탐지 모델(Faster R-CNN, RT-DETR)을 함께 조사하여, 왜 YOLO(정확히는 최신 버전인 YOLO26)를 baseline 모델로 선정하는지 근거를 마련하는 작업을 진행함. 중간 업무 보고서 작성도 함께 진행함.

## 진행한 작업

### 1. 중간 업무 보고 작성

업무요청서의 3개 과제(① 데이터 수집·준비 ② 객체 탐지 모델 조사·선정 ③ 학습 환경 설정) 진행 상황을 정리해서 보고.

- 보고서는 서술형 문장이 아니라 **개조식**(~완료, ~진행 중, ~예정 등 명사형으로 끝맺는 방식)으로 작성하는 게 표준이라는 걸 배움 — 빠르게 훑어보고 판단해야 하는 보고 받는 사람 입장을 고려한 형식
- "이번 주 목표" 항목은 계획만 간단히, 실제 상세 내용은 "수행 현황" 항목에 몰아서 구체적으로 쓰는 식으로 역할을 구분
- "완료"라고만 쓰지 않고 "Google Colab으로 학습 환경 설정 완료"처럼 구체적인 도구/방법을 명시하는 게 정보량이 많아서 더 좋음

### 2. 1-stage vs 2-stage 개념 학습

- **2-stage (예: Faster R-CNN)**: 1단계에서 객체가 있을 만한 후보 영역(region proposal)을 먼저 찾고, 2단계에서 각 후보의 클래스와 박스를 정교하게 계산. 두 단계를 거쳐서 정확하지만 느림
- **1-stage (예: YOLO, SSD, RetinaNet)**: 이미지를 한 번만 보고 위치+클래스를 동시에 예측. "You Only Look Once"라는 YOLO 이름 자체가 여기서 나옴. 빠르지만 전통적으로 정확도는 2-stage보다 낮다고 평가받았음 (최근 YOLO는 이 격차를 많이 좁힘)
- 실무에서 1-stage/2-stage를 가르는 기준은 속도·정확도 외에도 배포 환경(엣지 vs 서버), 객체 밀집도, 생태계/유지보수 성숙도, 라이선스까지 종합적으로 고려됨

### 3. YOLO26 조사

- 확인 경로: [공식 문서 모델 페이지](https://docs.ultralytics.com/models/yolo26) → [GitHub 저장소](https://github.com/ultralytics/ultralytics) (README, Releases 탭, LICENSE 파일) → 공식 Colab 튜토리얼
- 성능: COCO 기준 mAP 40.9~57.5 (n~x 스케일), 속도는 T4 GPU(TensorRT) 기준 1.7~11.8ms(≈85~588 FPS), CPU(ONNX) 기준 38.9~525.8ms
- 릴리즈 상태: GitHub Releases 누적 438회, 최신 릴리즈가 11시간 전 — 매우 활발하게 유지보수되는 정식(stable) 프로젝트임을 확인
- 라이선스: AGPL-3.0 (LICENSE 파일 원문 직접 확인)
- 튜토리얼 코드 확인: `!yolo train model=yolo26n.pt data=coco8.yaml epochs=3 imgsz=640` 한 줄이 핵심 — `data=` 자리에 우리가 01번 노트북에서 만든 `dataset.yaml`을 넣으면 바로 우리 프로젝트 학습으로 이어짐
- [YOLO 공식 라벨 포맷 문서](https://docs.ultralytics.com/datasets/detect/)에서 `class x_center y_center width height` (0~1 정규화) 스펙을 확인 — 01번 노트북에서 만든 라벨 변환 로직이 이 표준 스펙을 그대로 따른 것이었음을 검증함

### 4. Faster R-CNN 조사

- 확인 경로: [원논문(arXiv 1506.01497)](https://arxiv.org/abs/1506.01497) 초록, [torchvision 공식 문서](https://docs.pytorch.org/vision/stable/models.html)
- 성능: mAP 37.0 (torchvision `fasterrcnn_resnet50_fpn` 기준, 개선판은 46.7)
- 속도: 원논문 기준 VGG-16 모델로 GPU에서 5fps (2015년 당시 GPU 기준). [Detectron2 공식 Model Zoo](https://github.com/facebookresearch/detectron2/blob/main/MODEL_ZOO.md)의 최신 구현체(R50-FPN)로 재확인하면 **V100 GPU에서 0.038초/장 ≈ 26FPS** — 하드웨어/구현이 발전해도 실시간 기준(24~30fps)에 겨우 걸치는 수준이라 "오래된 자료라 불리했다"는 반박을 막을 수 있는 근거
- 라이선스: torchvision(BSD 계열) 사용 시 vs Detectron2(Apache 2.0) 사용 시 구현체별로 다름

### 5. RT-DETR 조사

- 확인 경로: [원논문(arXiv 2304.08069)](https://arxiv.org/abs/2304.08069) 초록, [공식 GitHub 저장소](https://github.com/lyuwenyu/RT-DETR)
- 성능: RT-DETR-R50 mAP 53.1% / 108FPS, RT-DETR-R101 mAP 54.3% / 74FPS (T4 GPU 기준)
- 논문 자체는 "속도·정확도 모두에서 기존 YOLO를 능가한다"고 주장하지만, 이는 2023년 당시 YOLO(v5/v8) 기준 비교였음. 같은 T4 GPU로 최신 YOLO26(2025년 출시)과 비교하면 YOLO26x가 mAP 57.5로 오히려 RT-DETR-R101(54.3)을 앞서, 최신 YOLO 버전에서는 RT-DETR의 우위가 사라졌음을 확인
- 라이선스: Apache-2.0

### 6. 비교표 정리 및 PPT 2페이지 초안 작성 (페어 비교 구조)

처음엔 3사 비교표를 한 페이지에 다 담으려 했다가, "YOLO vs Faster R-CNN(배제 이유)", "YOLO vs RT-DETR(차선 이유)"로 1:1 비교를 각각 한 페이지씩 나누는 구조로 변경 — 왜 배제/차선인지 근거가 더 명확하게 드러남.

**[p1] YOLO26 vs Faster R-CNN — 채택/배제 이유**

| 항목 | YOLO26 | Faster R-CNN |
|---|---|---|
| 구조 | 1-stage (탐지+분류 동시 예측) | 2-stage (① RPN 후보 제안 → ② 분류/박스 정교화) |
| mAP (COCO) | 40.9~57.5 (n~x 스케일) | 37.0 |
| 속도 (GPU) | 85~588 FPS | 최신 구현체(Detectron2) 기준 약 26 FPS (V100) |
| 라이선스 | AGPL-3.0 | BSD 계열 |

**구조가 곧 속도 차이의 원인**: 1-stage는 위치 예측과 분류를 한 번의 순전파로 동시에 처리해 별도의 후보 영역 생성 단계가 없는 반면, 2-stage는 후보 영역 제안과 분류를 순차로 두 번 거쳐야 해서 구조적으로 지연시간이 더 길 수밖에 없음. 다수의 CCTV 영상을 동시에 실시간 처리해야 하는 이 프로젝트 특성상, 1-stage 구조 자체가 2-stage보다 근본적으로 더 적합함.

**결론**: Faster R-CNN은 2-stage 구조상 최신 구현체·고성능 GPU(V100) 기준으로도 26FPS에 그쳐 실시간 CCTV 처리 요구사항 미충족 → **배제**. YOLO26은 1-stage 구조로 최소 스케일에서도 85FPS 이상 확보 가능 → **채택**.

**[p2] YOLO26 vs RT-DETR — 채택/차선 이유**

| 항목 | YOLO26 | RT-DETR |
|---|---|---|
| 구조 | 1-stage | Transformer 기반 (Self-Attention으로 후보영역 없이 직접 예측) |
| mAP (COCO) | 40.9~57.5 (x 스케일 57.5) | 53.1~54.3 |
| 속도 (GPU) | 85~588 FPS | 74~108 FPS |
| 라이선스 | AGPL-3.0 | Apache-2.0 |
| 생태계/유지보수 | 활발(438회 릴리즈), 공식 튜토리얼 충실 | 연구 공개 코드 수준, 튜토리얼 상대적으로 부족 |

**결론**: RT-DETR도 후보영역 없이 한 번에 처리하는 구조라 실시간 처리(74~108FPS) 자체는 가능함 — 즉 여기서는 구조 차이가 결정적 요인이 아님. 대신 YOLO26의 x 스케일(mAP 57.5)이 이미 RT-DETR-R101(54.3)을 앞서 성능상 뚜렷한 우위가 없고, 튜토리얼·생태계 지원도 부족 → **차선**. YOLO26은 성능·개발 편의성 모두에서 앞서 **최종 채택**.
- **YOLO26 → 최적**: 위 두 모델과 달리 기술적 결격 사유도, 대체 필요성도 없음

**[p2] Baseline 모델 선정: YOLO26**

선정 이유
1. 실시간성: T4 GPU 기준 최대 588FPS, 다중 CCTV 동시 처리 여유 확보
2. 성능: x 스케일 기준 mAP 57.5로 RT-DETR(54.3) 대비 우위
3. 개발 효율성: 활발한 유지보수(438회 릴리즈)와 공식 튜토리얼로 빠른 파이프라인 구축 가능

(참고: AGPL-3.0 라이선스 — 상업 배포 시 소스 공개 의무, 현재 실습 단계에는 영향 없음)

## 새로 배운 개념 / 리서치 방법론

- **모델 스케일(n/s/m/l/x)**: YOLO는 같은 구조를 크기별로 여러 버전 제공함 — nano(n) → small(s) → medium(m) → large(l) → xlarge(x) 순으로 파라미터가 커짐. 작을수록 빠르지만 정확도 낮고, 클수록 느리지만 정확도 높음. 벤치마크 표의 "mAP 40.9~57.5" 같은 범위 표기는 이 n~x 스펙트럼을 의미함. 프로젝트 요구사항(속도 vs 정확도 우선순위)에 맞춰 스케일을 고를 수 있음
- **속도 단위**: FPS(초당 프레임 수, 클수록 빠름) vs ms(장당 처리 시간, 작을수록 빠름). `1000 ÷ ms = FPS`로 서로 변환 가능
- **속도 비교 시 주의점**: 반드시 측정에 쓰인 하드웨어(GPU 종류, CPU 등)를 함께 확인해야 함 — 하드웨어가 다르면 숫자 비교 자체가 무의미
- **리서치 소스 우선순위**: 자동 요약/블로그보다 원문(공식 문서 벤치마크 표, GitHub LICENSE 파일, 논문 초록)을 직접 열어서 확인하는 습관이 중요 — 실제로 요약 도구가 준 정보를 원문 대조로 재확인한 경우가 있었음
- **GitHub에서 프로젝트 신뢰도 확인하는 법**: Releases 탭의 릴리즈 빈도·최신 날짜로 유지보수 활발도를 가늠할 수 있음

## 느낀 점 / 어려웠던 점
