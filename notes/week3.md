# 3주차

## 학습 내용

3주차 과제(FastAPI로 정체도 판단 API 구현)에 대한 피드백을 반영함. 피드백은 크게 세 가지였음: ① `area_ratio`/`avg_gap_px` 지표를 실제 물리량처럼 설명하지 말 것, ② 혼잡도 threshold(5%/15%)의 근거 마련, ③ 실제 CCTV 실패 사례를 조건별로 정리하고 어떤 데이터를 보강해야 하는지까지 연결. 세 가지 모두 감이나 추측이 아니라 실제 데이터로 검증하는 방식으로 진행함 ([코드 정리/03_FastAPI_colab사용_샘플코드.ipynb](../코드%20정리/03_FastAPI_colab사용_샘플코드.ipynb), [공유자료/03_FastAPI_colab사용_샘플코드.ipynb](../공유자료/03_FastAPI_colab사용_샘플코드.ipynb) 반영 완료).

## 진행한 작업

### 1. ① proxy 지표 한계 명시

`area_ratio`(탐지 박스 면적 합 / 전체 이미지 면적)와 `avg_gap_px`(차량 간 평균 최근접 거리)가 왜 "실제 물리량"이 아니라 "proxy 지표"인지를 정리함.

- **area_ratio**: 박스가 겹치면 중복 계산되어 과대평가될 수 있고, 버스·트럭 같은 대형차가 섞이면 차량 수는 적어도 면적 비율이 크게 올라감 → 실제 점유율이 아니라 **사진 간 상대적인 정체 경향**을 나타내는 지표로 설명
- **avg_gap_px**: 픽셀 단위 거리라 카메라 원근·해상도에 따라 같은 실제 거리도 다르게 찍힘 → 실제 거리(m)가 아니라 **상대적인 간격 경향**을 나타내는 지표로 설명

두 노트북의 FastAPI 코드 셀 바로 뒤에 마크다운 셀로 추가.

### 2. ② threshold 데이터 기반 재산정

기존 `area_ratio < 5 → smooth`, `< 15 → moderate`, `else → congested` 기준이 임의로 정한 값이라는 지적을 받아, 실제 CCTV 데이터로 검증함.

**데이터 확보**: `cctv뷰/New_sample.zip`에 AI-Hub "교통안전(Bbox)" 데이터셋(삼정고가교 BC1000801 카메라, COCO 포맷 라벨 + 원본 이미지)이 있는 것을 확인. 라벨 JSON에는 2,874장의 어노테이션이 있었지만 실제 이미지 파일이 포함된 건 750장이었고, 이 750장을 검증 대상으로 삼음. 이미지가 전부 1920×1080 고정 해상도라 area_ratio 계산 시 이미지마다 열어볼 필요 없이 JSON의 bbox 좌표만으로 계산 가능했음.

```python
import json, zipfile, os

z = zipfile.ZipFile("cctv뷰/New_sample.zip")
data = json.loads(z.read(JSON_PATH).decode("utf-8"))
avail = set(os.path.basename(n) for n in z.namelist() if n.lower().endswith(".jpg"))

for ann in data["annotations"]:
    boxes = ann["bbox"]  # [[x1,y1,x2,y2], ...]
    area_sum = sum((x2 - x1) * (y2 - y1) for x1, y1, x2, y2 in boxes)
    area_ratio = area_sum / (1920 * 1080) * 100
```

**분포 확인**: area_ratio 범위 0.00%~19.89%, 중앙값 1.97%, 90분위 5.78%. 기존 기준(5%/15%)으로 나누면 congested가 750장 중 1장(0.1%)뿐이라 사실상 안 쓰이는 등급이었음.

**경계 구간 육안 검증**: 백분위별 대표 이미지를 뽑아 직접 열어보며 확인.

| area_ratio | 육안 판단 |
|---|---|
| 1.97% | 한산 |
| 6.98% | 혼잡 아님 |
| 12.06% / 13.14% | 혼잡 |
| 19.89% | 완전 정체 |

6.98%(혼잡 아님)와 12~13%(혼잡) 사이에 실제 경계가 있다고 판단해 **moderate/congested 경계를 8.5%**로, smooth/moderate 경계는 중앙값 근처인 **2%**로 최종 설정.

| 기준 | smooth | moderate | congested |
|---|---|---|---|
| 기존 5% / 15% | 85.9% | 14.0% | 0.1% |
| 신규 2% / 8.5% | 50.8% | 46.3% | 2.9% |

검증 도중 부가 발견: 차량 6대뿐인데 대형차 포함으로 area_ratio가 10.49%까지 오르는 사진(`20201009_060005-090015_S_87615.jpg`)을 확인 → 1번 한계 설명(대형차 왜곡)에 추가로 반영.

두 노트북의 코드 셀 threshold 값을 `2 / 8.5`로 수정하고, 위 근거를 마크다운 셀로 정리해 추가.

### 3. ③ CCTV 실패 사례 정리 + 데이터 보강 우선순위

처음엔 "카메라 각도가 CCTV와 비슷하니 각도 문제가 실패 원인이겠다"고 막연히 생각했는데, 실제로는 학습 데이터 자체가 CCTV 앵글이 아니라 **데이콘의 synthetic(합성) 이미지, 그것도 대부분 수직에 가까운 항공뷰**였다는 걸 [code/01_데이터셋_구축_코드.ipynb](../code/01_데이터셋_구축_코드.ipynb)와 2주차 기록에서 다시 확인함. 이미 2주차에 이 부분을 검증해뒀던 걸 재발견한 것.

**핵심 실패 사례 (2주차 검증 결과 재확인)**: `cctv뷰` 폴더의 unsplash 실제 사진 6장으로 추론한 결과, synthetic test에서는 Precision/Recall 1.000이었는데 실제 사진에서는 차량이 여러 대 있어도 0~2대만 탐지됨. `imgsz`를 224→1280으로 올려도 비스듬한 각도(거리뷰) 사진은 개선이 없어서 **각도(시점) domain gap**이 근본 원인으로 확인됨. perspective/shear/degrees augmentation(exp3)으로 일부 완화했지만(`warren-valentine` 사진 탐지 0→1대), 해소는 아님.

**보조 실패 사례 (이번 주 CCTV 데이터 확인 중 발견)**:
- 대형차에 의한 area_ratio 왜곡 (위 threshold 검증 중 발견)
- 역광/그림자: 일몰 무렵 낮은 태양각으로 그림자가 길게 깔려 오탐(그림자→차량) 또는 미탐(그림자에 가려짐) 가능 (`cctv뷰/화면 캡처 2026-08-12 222544.png`에서 확인)
- 대형차에 의한 가림(occlusion): 같은 사진에서 큰 트럭이 차선을 가려 뒤차가 안 보일 수 있음

**데이터 보강 우선순위** (실패 사례와 1:1 연결):
1. 실제 각도(비스듬한 시점) 이미지 소량 라벨링 후 fine-tuning — 가장 근본적인 domain gap 대응
2. 다양한 조도/역광 조건의 CCTV 이미지 확보
3. 대형차 포함 이미지 라벨링 강화 (차종 구분 또는 가중치 검토)
4. 다른 CCTV 지점(카메라 각도·높이 상이) 데이터로 threshold 재검증 — 현재 임계값은 삼정고가교 1개 지점 기준

### 4. PT 자료 제작

위 세 가지 내용을 발표용으로 `python-pptx`를 이용해 `3주차_과제피드백_반영.pptx`(8슬라이드)로 정리함. 실제 검증에 썼던 이미지(AI-Hub CCTV 대표 샘플 3장, 2주차 unsplash 테스트 사진, 직접 캡처한 역광 사진)를 그대로 슬라이드에 삽입.

## 새로 배운 개념 / 궁금해서 짚어본 것들

- **zipfile로 압축을 풀지 않고 읽기**: `zipfile.ZipFile(...).read(경로)`로 압축을 통째로 풀지 않고도 안의 특정 파일(JSON, 이미지)만 메모리로 읽어올 수 있음. 569MB짜리 zip을 전부 풀 필요 없이 라벨 JSON만 읽어서 area_ratio를 계산할 수 있었음
- **COCO 포맷 라벨 구조**: `images`(파일 정보), `annotations`(bbox·category), `categories`가 분리되어 있고 `annotation.image_id` ↔ `image.id`로 서로 연결되는 구조. 이 데이터셋은 한 이미지당 어노테이션 1개에 bbox 리스트가 여러 개 들어있는 방식이라 일반적인 "1 bbox = 1 annotation" 구조와는 조금 달랐음
- **threshold를 데이터로 검증하는 방법**: 그냥 "적당해 보이는 숫자"를 고르는 게 아니라, 전체 분포(중앙값/백분위)를 먼저 보고 → 경계로 의심되는 지점의 실제 이미지를 육안으로 확인 → 그 결과로 숫자를 좁혀가는 순서로 접근한다는 걸 체득함
- **python-pptx**: `add_shape`/`add_textbox`/`add_table`/`add_picture`로 슬라이드를 코드로 직접 구성할 수 있고, `Inches`/`Pt` 단위로 위치·크기를 지정한다는 것을 익힘

## 느낀 점 / 어려웠던 점

threshold를 처음 정할 때는 그냥 "5%, 15% 정도면 적당하지 않을까" 하고 감으로 잡았던 건데, 실제 데이터로 분포를 뽑아보니 90분위조차 5.78%밖에 안 돼서 기존 congested 기준이 사실상 죽은 등급이었다는 걸 알고 놀랐음. 숫자 하나도 실제 데이터 없이는 근거가 안 된다는 걸 체감함.

또 실패 사례를 정리하면서 "학습 데이터가 CCTV 각도와 비슷하겠지"라고 막연히 넘겨짚었다가, 사실은 이미 2주차에 훨씬 정확하게(synthetic↔실제, Precision/Recall 수치까지) 검증해뒀던 내용이 있다는 걸 뒤늦게 발견함. 새 분석을 하기 전에 이전 주차 기록부터 다시 확인하는 습관이 필요하다고 느낌.
